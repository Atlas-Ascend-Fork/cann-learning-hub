## 2. 理论讲到什么程度

### 2.1 GMRES 求的是什么

给定稀疏矩阵 A 和向量 b，求 Ax=b。“稀疏”表示矩阵中大部分元素为零，程序用 CSR 只存非零值、列号和每行的起止位置。GMRES 适用于一般非奇异方程组，不要求矩阵对称正定。

从初始解 x₀ 出发，先计算残差 r₀=b−Ax₀。第 m 步只在以下空间中寻找修正：

\[
\mathcal K_m(A,r_0)=\operatorname{span}\{r_0,Ar_0,\ldots,A^{m-1}r_0\},\qquad
x_m=\arg\min_{x\in x_0+\mathcal K_m}\|b-Ax\|_2.
\]

可以这样讲：“每次迭代多找一个有用的方向，再把已有方向组合起来，让方程左右两边的差更小。”

Arnoldi 过程逐步构造互相正交的新方向，得到正交基 Vₘ，并满足 AVₘ=Vₘ₊₁H̄ₘ。大问题就转为一个小型最小二乘问题：求使 ‖βe₁−H̄ₘy‖₂ 最小的 y，再更新 x=x₀+Vₘy，β=‖r₀‖₂。源码用 Givens 旋转处理这个小问题。[理论出处：Saad 第 6.5 节](https://www-users.cse.umn.edu/~saad/IterMethBook_2ndEd.pdf)。

这里有两条需要说清的性质：精确算术下，不重启的 GMRES 对非奇异 n 阶矩阵至多 n 步得到解，最小残差随搜索空间扩大不增；实际使用 FP32 和重启版本，不能直接照搬这一保证。GMRES(m) 每轮最多保留 m 个方向，节省内存，但可能收敛变慢或停滞。[重启性质见同书 6.5.5 节](https://www-users.cse.umn.edu/~saad/IterMethBook_2ndEd.pdf)。

### 2.2 数学操作如何落到代码

代码里的 Host 指 CPU 主机侧，Device 指 NPU 设备侧，kernel 是提交到 NPU 执行的计算函数。

```mermaid
flowchart LR
  A[当前基向量] --> B[SpMV 计算 A乘v]
  B --> C[Dot 求已有方向上的投影]
  C --> D[AXPY 减掉投影]
  D --> E[Norm 与 Scale 得到新方向]
  E --> F[CPU 更新小型最小二乘问题]
  F --> G[更新解并复算真实残差]
```

| 操作 | 日常含义 | 本工程位置与成本 |
|---|---|---|
| SpMV | 稀疏矩阵乘向量 | Ascend C kernel；运算量约 O(nnz)，还要读索引、间接读取向量 |
| Dot / Norm | 求投影系数、向量长度 | 当前 `gmres_dot` 由一个 AI Core 完成，是优先观察的候选瓶颈 |
| AXPY / Scale | 把方向减掉、将长度归一 | NPU 上处理长向量；AXPY 指 y←y+αx |
| Givens / Hessenberg | 解一个远小于原问题的控制问题 | Host CPU 执行，长向量仍留在 NPU |
| 重算 b−Ax | 核实最终解是否真正满足方程 | 每轮解更新后在 Device 重算真实残差，标量返回 Host |

在长度为 m 的重启周期里，逐个方向正交化约需 O(nm²) 工作量，保存基向量约需 O(nm) 空间。这解释了为什么 restart 更大不一定更快。以本工程 FP32 基向量为例，U1 的 n=100000，仅 `(m+1)` 个基向量在 m=30 时约占 12.4 MB；这不是程序总显存。

双卡及以上时，各 rank（各个工作进程）拥有不同的行。源码把局部向量放入全局 Device buffer 的对应位置，其余位置为零，再用 **AllReduce 求和**形成完整向量；Dot/Norm 的局部标量也需要求和。当前路径不使用 AllGather。单卡直接使用本地向量，solve 内绕过这些跨卡规约。

MGS（改进的 Gram–Schmidt 正交化）每减掉一个方向，都要先得到投影系数，因而有顺序依赖。多卡下这会带来多次小消息同步；不能因为通信字节少，就认为通信耗时一定少。

### 2.3 残差小和解准确是两个检查

本工程生成已知真解 x*，再构造 b=Ax*，因此同时检查：

\[
\text{相对残差}=\frac{\|b-Ax\|_2}{\|b\|_2}\le10^{-6},\qquad
\text{相对解误差}=\frac{\|x-x^*\|_2}{\|x^*\|_2}<10^{-3}.
\]

残差是方程两边的差，解误差是答案与真值的差。对病态矩阵，小残差可能被放大成较大的解误差，因此不应只报“converged=yes”。本实验合成矩阵经过对角占优处理，也不能据此推断所有真实工程矩阵都一样容易求解。

### 2.4 时间怎样读才不误判

- `total_ms` 是一次 solve 的实际经过时间，包含本实现每次进行 RTC（运行时编译）及准备 Device 状态的成本；矩阵读取、分区和通信器初始化在 repeat 外。`--warmup` 只是丢弃额外 solve，不能称为只测热缓存下的 kernel。
- `spmv_ms`、`dot_ms` 等是 Host 包围 kernel 提交和同步的时间；`kernel_launch_ms`、`synchronization_ms` 与它们重叠，不能全部相加当总耗时，也不能据此画总和为 100% 的饼图。
- 多卡总时间按“每轮先取最慢 rank，再对多轮求平均”统计。阶段最大值可能来自不同 rank，阶段总和也未必等于总时间。
- Device 执行时间看 msprof 的 task/Timeline，即任务耗时和按时间排列的执行记录。只选择同一份、同一类数据进行统计，不能将所有 CSV 中的 API、task、汇总时间混加。

### 0:00–0:40：问题

### 0:40–2:30：算法为什么成立

（展示公式和迭代流程。）

GMRES 的思路是先猜一个解，再看方程左右差多少，这个差叫残差。接下来不断用矩阵作用在已有方向上，扩展可以搜索的范围。在当前范围内，选一个让残差长度最小的答案。这就是名字中“最小残差”的含义。

直接保存这些方向可能出现几乎重复的情况，所以需要正交化，让方向尽量互相独立。代码使用改进的 Gram–Schmidt：先算新向量在旧方向上的投影，再逐个减掉投影。Arnoldi 过程把原来的大问题变成一个小型最小二乘问题，程序通过 Givens 旋转处理它。

在精确算术下，不重启的 GMRES 随着搜索空间扩大，最小残差不会增加；非奇异 n 阶问题至多 n 步得到解。但保存的方向越多，内存和正交化成本也越大。本实验用 restart=30，每轮最多保留 30 个搜索方向，然后重新开始。因此省下内存的同时，也可能丢掉有用的搜索信息。实际浮点计算和重启之后，不能直接套用不重启版本的收敛保证。

### 2:30–4:00：代码怎样执行

（指向 SpMV、Dot、AXPY、Norm 流程。）

一次迭代先做稀疏矩阵乘向量，也就是 SpMV；再通过 Dot 求投影，通过 AXPY 减去投影，最后求长度并归一化。长向量计算在 NPU 上，小型最小二乘和迭代控制在 CPU 上。

这几步的成本不同。稀疏乘法不仅计算，还要读取列索引和不连续的向量位置。正交化则要依次处理越来越多的旧方向。重启长度为 m 时，保存基向量大约需要 n 乘 m 的空间，一个周期的正交化工作量大约为 O(nm²)，也就是 n 乘以 m 的平方。所以增大 restart 可能减少重启，却未必减少总时间。

以本次十万阶矩阵为例，31 个 FP32 基向量约占 12.4 MB。这只是基向量的空间，程序还有矩阵和其他缓冲区。

### 4:00–6:00：怎样判断结果

（展示正确性公式和计时说明。）

先说正确性。程序生成了已知真解，再构造右端项，因此能做两个检查：相对残差看方程两边是否接近，相对解误差看答案是否接近真解。这里分别要求不超过百万分之一和小于千分之一。对病态矩阵，小残差不一定代表小解误差，所以两项都看。

再说时间。当前实现每次 solve 还包含运行时编译和设备状态准备，因此 solve 的总时间不能当成纯算子时间。阶段计时里又包含提交和等待，与同步时间有重叠，不能把所有列相加。

虽然工程支持分布式运行，今天展示的是单卡。多卡时需要合并向量和投影标量，当前代码用 AllReduce 求和；单卡直接绕过跨卡规约，所以看到通信次数为零是正常的。我们这次尚未测多卡，也没有做分区策略的性能对照。

## 9. 可能被问到的问题

- **为什么用 GMRES，不用共轭梯度法？** GMRES 适用范围不要求对称正定；标准共轭梯度法要求这些条件。具体算法仍应根据矩阵性质选择。
- **标题是分布式，为什么只跑一张卡？** 本次先验证设备计算和单卡正确性；多卡通信、负载均衡及扩展效率尚未实测，属于后续实验。
- **32 次迭代怎么超过 restart=30？** 30 是一个重启周期的上限，总迭代可以跨越多个周期。
- **为什么不能把 Dot 和同步相加？** Dot 的主机计时已经包含等待，属于同一时间段的不同观察方式。
- **这次加速了多少？** 尚无优化前后对照，不能给出加速比；3.21 秒是当前配置的平均 solve 时间。
