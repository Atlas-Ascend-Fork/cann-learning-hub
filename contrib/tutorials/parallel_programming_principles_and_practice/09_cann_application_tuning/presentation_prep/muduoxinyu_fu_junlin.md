## 2. 理论讲到什么程度

### 2.1 Attention 和 KV cache

单个注意力头的核心计算是：

\[
O=\operatorname{softmax}\left(\frac{QK^T}{\sqrt d}\right)V.
\]

Q 可以理解为“当前要查什么”，K 是历史内容的索引，V 是对应内容；Softmax 把相关程度变成非负、和为 1 的权重。除以 √d 用来控制点积尺度，减少分数过大导致的 Softmax 饱和。

本实验是逐 token 解码，即每次生成一个模型使用的文本单位，它不一定对应一个汉字。当前 Q 的序列长度为 1，K、V 来自截至当前位置的缓存。每步只追加新的 K、V，不重新计算全部历史 K、V。对长度 T、头维度 d 的单头，本步 Attention 主计算随 Td 增长；不要把整段序列 Attention 的 T² 中间矩阵直接套到这个单 token 场景。

### 2.2 两条实现到底改了什么

FP32 和 FP16 分别用 32 位、16 位保存浮点数；后者更省空间，但可表示的精度和范围不同。Cast 是浮点类型转换。

| 项目 | Path A | Path B |
|---|---|---|
| Attention 数据类型 | FP32 | FP16 |
| 主要计算 | 分解的多算子 Attention | `aclnnIncreFlashAttentionV4` |
| KV 路径 | FP32 KV 路径 | 新增并使用持久 FP16 KV cache |
| 转换 | 原 FP32 数据流 | Q、K、V 转 FP16，输出再转 FP32，每层每步 4 次 Cast |
| 开关 | `--backend npu --enableDeviceOpt` | 同左，加 `--useNpuFlashAttention` |

可以直接展示 [课程 A/B 示意图](../02_muduoxinyu_optimization/images/attention_path_ab.svg)，再打开下载源码中 `src/backend/npuBackend.cpp` 的 `attentionAllHeadsFlashDevice`。

B 的实际顺序是：Q/K/V 转 FP16 → 将当前 K/V 追加到缓存 → 执行增量 FlashAttention → 输出转回 FP32。Q 的布局为 `[1, heads, 1, headSize]`；BNSD 分别表示批量、头数、序列长度、头维度。缓存容量按 maxSeqLen 分配，但本次有效长度通过 `pos+1` 传入。

FP16 的每个缓存元素占 2 字节，FP32 占 4 字节，因此同形状的单份 KV 数据字节数减半。实际进程还可能保留其他缓冲区、原缓存或临时区，**不能据此声称总显存减半**。

### 2.3 FlashAttention 为什么可能更快

FlashAttention 的核心思路是分块计算，尽量让中间结果留在更快的片上存储里，减少向高带宽显存反复读写。分块 Softmax 维护最大值与指数和，合并分块时重新缩放，因此不需要为了分块而改成近似 Attention。[FlashAttention 原论文，第 3.1 节](https://arxiv.org/html/2205.14135v2)。

“精确 Attention”指数学目标没有换成稀疏近似等其他算法，不代表 FP16 和 FP32 每一位都相同。这里还同时改变了精度、缓存和算子组织；测到的差异只能归于**整体实现方案**，不能单独说成融合的收益，也不是一次模型量化实验。

本例 batch=1、query 长度为 1，算子规模较小。节省的中间访存与下发成本，可能被四次 Cast、张量描述和临时工作区准备、缓存搬移和启动固定成本抵消。融合名称本身不能保证整个程序加速。Attention 之外的模型运算也限制了总收益：若 Attention 原占总时间的 f，即使这一部分无限快，总加速仍不超过 1/(1−f)。

### 2.4 怎样验证功能和性能

课程固定模型、tokenizer、prompt、steps、temperature=0、topP=1、设备和统计方式。先做 A→B 的 12 步功能检查，再按 B→A 做 120 步性能测试。性能阶段输入文件有 4 行 `hello`，第 1 个 sample 预热，取第 2–4 个 sample 的吞吐率统计。

| 检查 | 说明 |
|---|---|
| token exact | A/B 在这些输入上生成的 token ID 序列完全一致；不等于所有输入或中间浮点数都相同 |
| marker | 日志确实走了声明的 A/B 路径 |
| fallback=0 | 没有退回另一条实现路径 |
| 调用次数 | 本脚本按 12 层×12 步，期望 144 次 FA、576 次 Cast |
| flash_sync_count=0 | 检查此 FlashAttention 路径的显式同步计数，不代表全程序没有同步 |
| mean 与 CV | 平均吞吐率（每秒生成的 token 数）与相对波动；CV=总体标准差/均值×100% |

\[
\Delta=\frac{\operatorname{mean}(B)-\operatorname{mean}(A)}{\operatorname{mean}(A)}\times100\%.
\]

`functional_pass` 表示功能检查通过；`performance_valid` 表示采样结构、有效数值、token 和错误检查通过；`performance_beneficial` 还要求 Δ>0。**当前分析器没有用 CV 大小或显著性检验判定性能有效性。** 差异如果与波动相近，应增加独立轮次、交换顺序后再下结论。三次采样的微小正值不能自动说明有稳定收益。

## 8. 可照读讲稿（约 12 分钟，含现场操作）

括号内是操作提示，不需要念出来。现场运行前先彩排计时；完整 A/B 超出预算时，按第 5 节展示课前保存的完整结果。

### 0:00–0:40：实验问题

大家好，我是傅俊林。我负责 MuduoXinyu 推理优化实验。这个轻量级推理框架来自 BNU-SYS，我们使用公开的课程复现仓库。今天对比同一个模型的两条 Attention 路径：一条用 FP32 多算子，另一条用 FP16 FlashAttention。我们既看生成结果是否一致，也看整个生成过程有没有更快。

### 0:40–2:10：Attention 和缓存

（展示 Attention 公式。）

生成下一个 token 时，模型需要从历史内容里找相关信息。可以把 Q 理解成当前的问题，K 是历史内容的索引，V 是内容本身。先用 Q 和 K 算相关程度，再经 Softmax 变成权重，最后对 V 加权得到结果。除以头维度的平方根，是为了控制点积尺度。

模型逐个生成 token，之前算过的 K 和 V 可以缓存下来，每一步只追加新内容。这就是 KV cache。我们的场景里，每次只有一个当前 query，所以是在一个当前位置与历史缓存之间计算注意力，不能直接套用整段序列同时计算时的平方规模中间矩阵。

### 2:10–4:00：两条路径的区别

（打开 A/B 示意图，指向四次 Cast。）

A 路径使用 FP32，拆成多个算子执行。B 路径调用增量 FlashAttention，但为了接入它，程序先把 Q、K、V 转成 FP16，再把输出转回 FP32，因此每层每步有四次类型转换。B 还维护持久的 FP16 KV 缓存。

这意味着本次同时改变了精度、缓存和算子组织。最后看到的吞吐差异，是整套实现的结果，不能全部归因于算子融合。

FP16 每个元素占两字节，FP32 占四字节，所以同形状的一份缓存可以少一半字节。但实际程序还保留其他缓冲区，不能据此说整个模型的显存减半。FP16 的数值范围和精度也与 FP32 不同，所以替换之后必须重新检查输出。

### 4:00–6:00：为什么可能变快，怎样验证

FlashAttention 通过分块组织计算，让中间结果尽量留在更快的片上存储里，减少反复读写显存。它使用分块 Softmax，并在合并时调整缩放，保持相同的数学目标。“精确 Attention”说的是没有换成近似算法，并不代表两种浮点实现逐位相同。

这次 batch 为 1，每步 query 长度也是 1。计算规模较小时，四次类型转换和算子启动等固定成本可能占很大比例。即使 Attention 自己变快，模型其他部分还要执行，因此端到端收益也会受到限制。

我们固定真实模型、分词器、输入、生成步数和采样参数。先做 12 步的短功能检查，对比 token、路径标记和调用次数；再进行 120 步性能测试，每条路径跑四个 sample，第一份预热，后面三份统计。

这里有三个不同的问题：功能是否通过、数据是否满足比较条件，以及这轮均值是否提高。它们对应结果里的三个判定字段，不能只看一个 PASS 就宣布优化成功。

先看功能字段。token exact 表示在这些固定输入上，两条路径生成的 token 编号完全一致。再看调用次数：12 层乘 12 步，应该有 144 次 FlashAttention；每次四次转换，所以是 576 次 Cast。fallback 为零，表示没有退回另一条路径。这里的同步计数只针对被记录的 FlashAttention 路径，不代表整个程序没有同步。

## 9. 可能被问到的问题

- **token 一致是否证明两个实现完全等价？** 只证明本次固定输入的生成序列一致，不证明全部输入或中间浮点值一致。
- **FlashAttention 是近似计算吗？** 算法保持原 Attention 的数学目标；实际浮点精度和计算顺序仍会造成数值差异。
- **为什么融合后反而略慢？** 本次计算规模较小，转换与启动成本可能抵消收益；这只是待验证的解释，具体原因还需算子级测量。
- **`--skipValidation` 是否跳过了所有检查？** 它跳过程序内部原有验证；课程脚本仍独立比较 A/B token、路径、调用次数和错误信息。
- **120 steps 为什么日志是 119 个生成 token？** 本程序的步骤与生成 token 计数口径不同，统计采用日志的真实生成数量；不手工补成 120。
- **为什么与 HiDevLab 的 +4.88% 不同？** 驱动、系统和编译环境不同，两次也都有采样波动，不能只凭两个均值判断平台优劣；课堂使用本次 CANNLab 的 +1.14%，并同时说明波动。
